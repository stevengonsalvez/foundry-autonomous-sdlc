The short version

  • You file a GitHub issue. Agents do the rest, all the way to prod. Score the requirement, check an agent can build it, write failing tests, build until green, review, merge, release. Then the change is staged, smoke tested, soaked for 10 minutes and promoted, or rolled back. No human step.
  • Code decides, models answer narrow questions. A deterministic orchestrator moves labels and owns every merge and every promotion. Models only return JSON that code re-checks. CI runs six plain checks and drives nothing.
  • Three parts were added after the first run. A state-keeper agent, sdlc-ledger, the only writer of branch state. A CD pipeline with staging, smoke, soak, prod and rollback. A read-only control center that shows all of it.
  • The money part is not good news. The pipeline estimated 1.86 USD. Azure billed 4.80 USD at first read and 13.02 USD a day later, so the original 5 USD cap was already exceeded. The owner then set the caps to 25 USD total, a 22 USD halt and 3 USD per issue, later raised to 35 USD total and a 32 USD halt. 13.02 USD is inside both. See section 9.
  • Read it top down. One overview, how to file an issue, the lifecycle, then the loop, the coder, the PR repair loops, delivery, the data plane, the control center, where it runs and what it costs.

How to put an item on the backlog

1
Open the formissues/new/choose, pick Feature request or Bug report. It must be the repo owner: issues from anyone else are ignored with zero spend.
2
Fill it so a test can check itFeature: Goal, Acceptance criteria (one testable statement per line), Scope, Edge cases. Bug: Steps to reproduce, Expected, Actual, Where you saw it.
3
SubmitThe form adds type:feature or type:bug. The next five-minute tick picks it up. The control center shows it as a "waiting for ledger" card within about a minute while the GitHub API budget lasts.
4
Watch the labels, or the boardThe orchestrator swaps stage:* labels and edits one state comment in place. The PR that appears says Closes #N.

What scores 80 or more

  • A clear goal: who gets what, and why.
  • Numbered, testable acceptance criteria with exact strings and values.
  • Scope: what is in and explicitly out.
  • Edge cases: empty, null, malformed.
  • Passes first time: issue #12 (context, user story, numbered criteria, scope).
  • Bounced: issue #24 scored under 80. Questions, simulated owner answers, re-score, then it built.

From a terminal instead

  • The CLI cannot fill a form template, so pass the label yourself and write the same sections in the body.
  • The Routine is disabled now (hosted compute is the whole bill, and the spend cap is already exceeded). Enable it only after raising the cap.

1. The heartbeat: one orchestrator tick

Everything is driven by one loop. Nothing else decides what happens next.

Swipe the diagram sideways to read it at full size.

agent or workflow doing the workstep or piecestop, escalation or rollbackNEW: added after the first run

The orchestrator has no memory between ticks. It rebuilds the picture from GitHub every time, which is why a crash mid-tick loses nothing. Its compute stops 2 minutes after the tick ends.

2. Questions back, feasibility, tests first

Three agents act before any code exists. Their output is checked in code before the next step sees it.

Questions back

  • sdlc-req-gate scores goal, testable criteria, scope and edge cases from 0 to 100.
  • Under 80: it posts questions and the ticket sits in stage:needs-refinement.
  • sdlc-product-owner answers. Every reply is labelled as a simulated product owner.
  • Score again. Two rounds without 80 ends in escalated:requirements.
  • Bugs are triaged first: severity s1 to s4 and an owner. The control center keeps the Q and A in its review trail.

Feasibility and tests first

  • sdlc-feasibility reads the repo (read-only) and says if an agent can do the work. If not: escalated:not-agent-suitable with reasons, such as production keys, DNS and firewall changes, vendor sign-off.
  • sdlc-test-designer writes failing tests. Code checks the path, the vitest imports, that every import exists and that tsc passes. One re-ask if not.
  • The designer never sees the coder, and the coder may not change the designed tests. That is what makes "tests first" real.

3. The coder: what agy is and what it does

The coder is a hosted agent whose job is to run a coding CLI safely. agy is the Antigravity CLI, a plan-backed coding agent that only edits files.

Swipe the diagram sideways to read it at full size.

agent or workflow doing the workstep or piecegood end

Everything around agy (git, tests, scope rules, the PR) is ordinary code in the runtime, because a coding CLI is not trusted to police itself. Each green round is pushed as a checkpoint, so an interrupted job resumes from the branch instead of starting over.

4. After the PR: review and repair loops

Three different things can send a PR back. Each has its own cap.

Swipe the diagram sideways to read it at full size.

agent or workflow doing the workstep or piecegood endstop, escalation or rollback

Maintenance is the same loop on a PR the owner opens (label maintenance:test-repair): the coder may only touch the test files that failed, and pushes one squashed commit once they pass.

5. Delivery: from merge to prod, no human

A merged PR reaches /staging/ by itself. It reaches prod, the site root, only after Playwright smoke on staging and a 10 minute soak. Any failure rolls back to the previous build and flags the ticket. Details: docs/cd.md.

Swipe the diagram sideways to read it at full size.

agent or workflow doing the workstep or piecegood endstop, escalation or rollbackstored in a branch of the repoNEW: added after the first run

Prod changes in one place only, promote, and only when stage, smoke and soak all succeeded for that sha. A PR can never alter its own CD: workflow_run workflows run from the default branch. Promotion copies the already tested staging artifact, it never rebuilds.

Rollback, by what failed

  • Stage, smoke, soak: staging goes back to what prod holds, prod is untouched.
  • Promote after its push: prod goes back to prod-prev/.
  • First release ever: staging is removed, and prod too if it was just promoted.
  • The ticket gets escalated:deploy-failed, which the orchestrator treats as terminal.

What the soak does not prove

  • It is 10 minutes of synthetic probes, not real traffic. It catches a bad deploy or a flapping CDN, not a bug only users hit.
  • Pages is a CDN: a visitor may see the old build briefly, so live checks poll for up to 6 minutes.
  • One Pages artifact serves every path, so a broken pages.yml run blocks all of them.

6. The ledger and the data plane

The ledger is a small hosted agent that keeps the books. It is woken by events, folds them into state, commits to branch state and goes back to sleep.

Swipe the diagram sideways to read it at full size.

agent or workflow doing the workstep or piecestored in a branch of the repoNEW: added after the first run

The ledger sums with code and never lets a model invent a number: a model writes only a one line summary, shown while the ticket's digest still matches. Sizing: 0.25 vCPU, 0.5 GiB, idle timeout 2 minutes (the platform minimum), so between events it bills nothing. Fallback: LEDGER_MODE=inline runs the same class inside the orchestrator with the same schema; off sends nothing.

7. The control center

A static app in the same repo, published at /control-center/. It replaces the single metrics page as the thing a person looks at, and the old dashboard still publishes beside it.

Swipe the diagram sideways to read it at full size.

step or pieceNEW: added after the first run

It only draws what state.json says and never invents data. If the data is older than 10 minutes a banner says so, and GitHub stays the source of truth.

8. Where it runs

One Azure resource group, one public GitHub repo, no private networking.

Swipe the diagram sideways to read it at full size.

Hosted agents are billed while a session is alive and until it idles out, so the idle timeouts are set to the minimum that works: 2 minutes for the orchestrator and ledger, 10 for the coder.

9. Cost, honestly

The pipeline's own number was wrong by a factor of seven, and the cap it was meant to enforce was already broken.

Swipe the diagram sideways to read it at full size.

step or pieceagent or workflow doing the workstored in a branch of the repoNEW: added after the first run

What happened

  • The orchestrator priced hosted sessions at the Foundry meter only. Azure bills the same session again as Container Apps usage, and keeps it billed until it idles out.
  • The first Azure read, 4.80 USD, was taken before billing lag caught up. Read again on 2026-10-11 it was 13.02 USD. The Azure budget only alerts, it does not stop spend.
  • The halt watches the orchestrator's estimate, not the bill, so it cannot protect the cap by itself. The control center shows both, and the runbook says to check the bill before spending.

What changed

  • The cost model now uses both meters and charges one idle tail per finished coder job. The coder idle timeout went from 30 to 10 minutes.
  • The ledger reads Azure Cost Management and puts the estimate and the bill side by side in cost.gap, so the gap is shown, not hidden.
  • No new tick, coder job or model call was started to finish this work, the routine stays disabled, and the ledger's own spend is bounded to cents. Details: decision D14.

Gates, merge rule and caps

GatePasses when
testlint, typecheck, unit, component and contract tests pass
coverageline coverage across app/ is at least 80 percent
e2ePlaywright passes against the built app and mock carrier
gitleakszero findings in the PR range and working tree
tdd-orderfirst commit is tests only, red for an assertion, and later commits do not edit those tests
agent-scopeon agent/* branches every changed file is under app/
smokePlaywright on the live staging URL: heading, tracking timeline, not-found alert, build sha, no console errors (CD gate)
soak10 minutes of probes every 30 seconds with no repeated failure (CD gate)

The orchestrator merges only if

  • all six checks are green on the head sha
  • the reviewer approved that exact sha
  • issue and PR are owner-authored
  • branch is agent/* or labelled maintenance:test-repair
  • every changed file is on the allow-list (app/)
  • cost is under the cap

Guardrails

  • 3 USD per issue, then escalated:cost-cap
  • 32 USD total estimate, then no new work (35 USD hard cap) (the estimate undercounts, see section 9)
  • Coder job: 7200 s deadline, 5 iterations
  • agy runs as an unprivileged user; any symlink, .git change or out-of-scope edit is reverted and fails the job
  • Prod changes only in promote, after stage, smoke and soak
  • PAT never in git config, URL or logs; commits are merge commits

How to check the claims

1
Were the tests written first?Open any agent PR above. The first commit is tests only and red for an assertion; the tdd-order check fails the PR otherwise.
2
Did a second agent mark it?The reviewer's verdict names the exact head sha it approved, so an approval cannot carry over to a later push.
3
Is there a secret in the bag?gitleaks runs in CI and was run over the full history: no leaks.
4
Is the shop open?The app and dashboard URLs below answer 200. Staging, prod and the control center need the CD and ledger work to be merged and run first.
5
How much did it really cost?Do not trust the pipeline's number. Ask Azure Cost Management for the resource group, as the runbook and the findings describe, and compare it with cost.gap.

Honest limits

Cost
Azure billed 13.02 USD for the resource group on 2026-10-11 against the original 5 USD cap. The first read, 4.80 USD, was early. The pipeline's estimate said 1.86 USD, and the Azure budget only alerts, it never stops spend. On 2026-10-12 the owner set the caps to 25 USD total, 22 USD halt and 3 USD per issue, later raised them to 35 USD total and a 32 USD halt.
Status
On 2026-10-11 the ledger, CD and control center went live: branches state and deploy exist, the hosted sdlc-ledger writes state, and CD promoted a real merge to prod and rolled back a forced smoke failure. A new ticket was not run live through building and review, because the Azure cap was already spent before this work began.
Getting here
17 issues and PRs were escalated while the system was hardened. Each one was a real defect found by running the demo; all are listed in the evidence.
Security
The GitHub PAT reaches every repo of the owner account, not one (the clients hard-code this repo). Coder commits are unsigned. Public endpoints with Entra-only auth, no private networking.
Delivery
The soak is synthetic probes against staging. Prod serves the same bytes staging did, so it cannot catch a bug only real users hit.
Unverified
Whether the agy plan-token terms allow cloud use. Nothing in the repo settles it.
Still live
The Azure stack in rg-fsdlcd-demo and its state group. The routine is disabled. terraform destroy removes it.
